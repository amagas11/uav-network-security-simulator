# 射频指纹第二阶段：接收准入、物理防御与结果上报

## 1. 当前完成的内容

在第一阶段“生成带噪指纹并识别本跳发送设备”的基础上，加入了接收端实际丢弃、压力触发的严格白名单、成员机到中心的告警传输，以及单独的物理层评估。前端未改动，没有新增模型训练或生产依赖。

仍然是特征级仿真：没有真实 IQ 波形，指纹不是业务报文字段，质量也是仿真量。指纹生成、模板注册和距离计算见 `rff_observe_only_guide.md`。这里的白名单是每个接收端注册过的合法直接邻居，不是整个编队所有设备的通用列表。

默认 `rff_policy_mode="OBSERVE_ONLY"`，仅保存判断，不因为 RFF 产生丢包、告警报文或防御动作。必须显式设置 `ENFORCE` 才会执行新防御。两种模式都可以看到“如果启用会不会丢弃”，但只有实际执行成功才记为已丢弃。

## 2. 一帧完整的接收流程

```text
本跳发送设备发射无线帧
  -> 现有 PHY 仿真产生 SINR、测量质量和解码结果
  -> 仿真器用本次发射设备的私有特征生成接收端带噪指纹观测
  -> 接收端用本地合法邻居模板识别，与本跳声明 ID 比较
  -> 解码成功：先计入接收总到达率，再执行 RFF 准入判断
  -> ENFORCE 且需丢弃：记录实际防御结果，不进 HMAC、不进正常接收队列
  -> 允许：有上层协议时继续原有认证、接收队列与业务流程
           无上层协议时只排队、透明转发或记录到达，不解读或执行业务
```

解码失败时也可以保存仿真的指纹观测及身份异常证据，但不能把一个本来就没解码出的帧记成“执行了丢弃”。物理模块不使用攻击类型、实际攻击源、无噪声特征、载荷、HMAC 或序列号来作判断。

多跳时比较当前一跳：`成员 2 -> 领航 1 -> 中心 0` 的两次指纹应分别匹配设备 2 和设备 1。不能用一直为 2 的端到端业务源地址来比较第二跳。

## 3. 检测与防御规则

### 3.1 单帧身份异常

质量达到阈值、存在有效本跳声明，且出现以下一种情况，就保存通用的 `RFF_IDENTITY_MISMATCH` 身份异常：

- 指纹可靠匹配另一台合法设备，其 ID 与声明不一致。
- 所有合法模板都不能接受这个指纹，识别原因是 `NO_TEMPLATE_WITHIN_THRESHOLD`。

ENFORCE 下单帧即可丢弃，无须等待多帧投票。第二种情况只说明“不是可接受的合法邻居指纹”，不表示接收端知道外部攻击者的真实 ID。低质量、多个候选接近、缺少声明、缺少模板或缺少观测，不直接认定为攻击。

外部伪装、外部修改载荷后重发的 FDI、外部重放都可能留下相同的身份异常。在线模块不能仅据此准确区分这三类攻击，分类统计在离线评估完成。

### 3.2 压力下的严格白名单

接收队列占用比例达到 `rff_queue_pressure_ratio`，或者总到达速率达到现有 `flooding_packet_rate_threshold_pps`，进入 `RFF_STRICT_WHITELIST`。速率触发可由 `rff_strict_on_rate_alarm=False` 关闭，它不依赖旧的应用层 Flooding 告警是否启用。

严格状态只放行“质量合格、指纹与声明 MATCH、声明身份和识别身份都在本地白名单内”的帧。未知、模糊、低质量和缺失输入均不能通过；未确认身份异常的这类丢弃标成 `RFF_STRICT_UNVERIFIED`，属于保护性措施，不算确认攻击。

正常状态也会丢弃已确认的身份异常。压力触发的是更严格的未知来源准入，而不是到压力发生后才生成指纹。两者均不引入令牌桶或业务优先级。

队列和速率都恢复正常后，需连续保持 `rff_strict_hold_s` 秒才退出严格状态；中间再次有压力就重新计时。没有新帧时也会按仿真时钟检查恢复。进入和退出都保留事件并上报。

### 3.3 能力边界

| 情形 | 本阶段能做什么 |
| --- | --- |
| 外部设备伪装、FDI 重发、重放 | 检查本跳物理身份，合格异常样本在进入业务处理前丢弃 |
| 外部 Flooding | 确认的未知或不一致来源可直接拒绝；压力下启动严格白名单 |
| 合法设备被入侵，使用自身无线硬件发送恶意业务 | 指纹可能仍匹配，不声称检出；有上层协议时由原有完整性或业务规则补充 |
| 合法设备自己重放、或合法设备制造过量流量 | 指纹可能仍匹配，单靠白名单不能彻底防御；上层检查仍有价值 |
| 干扰型 DoS | 指纹准入不能消除射频干扰；原有物理信道干扰逻辑不由本模块替代 |
| 完全被动窃听 | 不产生新发射，不做 RFF 检测或虚构定位 |

## 4. 无上层协议模式

`application_layer_available=False` 表示接收端无法解读业务协议。业务帧的源地址、序列号、会话号、载荷等上层在线投影置空，`availability.missing_reason` 为 `APPLICATION_PROTOCOL_UNAVAILABLE`。仍保留已知的本跳声明地址、链路标识和帧大小。

业务接收不调用解密、HMAC、重放或业务规则，不更新遥测状态、执行指令或增加正常业务执行成功数。透明转发只利用仿真器已知的路由元信息搬运原始受保护字节，刷新当前一跳的链路头，并产生新一跳的指纹观测。它不代表实现了未知厂商协议的路由解析。目的节点增加独立的 `opaque_delivered_count`，不能把它解释为业务被正确执行。

平台自己的 `SECURITY_REPORT`、`SECURITY_SUMMARY`、`SKG_CONTROL` 是我们掌握的管理协议，仍正常认证和解析。因此“不开放无人机业务协议”不等于中心不能接收我们自己的安全告警。两者必须区分。

## 5. 输出与中心上报

每帧接收事件的 `extensions.rff_decision`：

| 字段 | 中文解释 |
| --- | --- |
| `identity_result` | MATCH、MISMATCH、UNKNOWN 等识别结果 |
| `policy_state` | 本帧判断时的 NORMAL 或 RFF_STRICT_WHITELIST 状态 |
| `would_drop` | 按规则应当丢弃，即使当前只是观察也会计算 |
| `drop` | 本次实际执行了物理准入丢弃；失败解码或动作失败时为 false |
| `confirmed_identity_anomaly` | 是否有质量合格的身份异常证据，不等同于低质量保护性拒绝 |
| `reason` | 放行或拒绝原因代码 |
| `transition` | 本次是否触发 ENTER_STRICT 或 EXIT_STRICT |
| `decision_time_s` | 以仿真秒计的判断时间 |
| `quality` | 本次指纹模拟观测质量 |
| `packet_rate_pps` / `queue_ratio` | 本接收端总到达速率、接收队列占用比例 |

`extensions.air_emission_ref` 是本次空口发射 TX 事件的不透明编号，用来关联具体的一次发射，不包含攻击标签或真实源 ID。`DEFENSE_RESULT` 保存执行结果及其接收证据编号。节点安全状态另外提供 `rff_policy_state`、`rff_strict_since_s`、`rff_clear_since_s`。

确认异常、严格保护性拒绝及状态切换会生成本地安全报告。重复异常按 `security_summary_window_s` 限频，每帧原始证据仍完整记录；状态进入、退出各上报一次。沿既有的 `成员机 SECURITY_REPORT -> 领航机聚合 -> SECURITY_SUMMARY -> 中心` 路径传输，中心自身发现的异常按现有中心本地处理路径记录。报告不直接跳进中心收件箱，链路中断会影响送达时间。聚合后的报告保留物理身份、压力、动作结果和证据编号。

在现有接口中读取：`GET /api/runtime` 查看中心实际收到的安全报告；`GET /api/evaluation` 的 `physical_layer` 查看独立物理评估；原始接收与防御证据可从导出的 `events.jsonl` 获取。现有上层评估字段保留原义，不用物理层成功率去覆盖。

物理评估通过私有发射记录和独立攻击标签，离线关联具体的目标接收。只有外部重发、目标实际收到、有合格指纹和本跳声明的样本进入对应检测统计；能解码的合格样本才算丢弃机会。被动窃听、内部合法硬件攻击、无接收或无合格观测返回不可评估原因，分母为零时比率为 null。`protective_unverified_drops` 单独统计保护性拒绝，不混入确认检测。OBSERVE_ONLY 不记实际防御成功。

## 6. 启用示例

通过 `POST /api/runs` 创建实验，可增加：

```json
{
  "duration_s": 10,
  "auto_advance": false,
  "rff_enabled": true,
  "rff_policy_mode": "ENFORCE",
  "application_layer_available": false,
  "rff_queue_pressure_ratio": 0.6,
  "rff_strict_hold_s": 2.0,
  "rff_strict_on_rate_alarm": true
}
```

有上层协议并希望两层同时工作时，把 `application_layer_available` 改为 true；此时 RFF 先准入，通过后再走原有应用检测。Python 代码同样使用 `RunConfig` 的这些字段。

默认质量阈值 0.45、距离阈值 3.0、候选间隔 0.5、注册样本数 20 均沿用第一阶段，不是来自真实无人机校准。ENFORCE 要求 RFF 已启用并使用同步模板识别器；显式传入外部异步 `rff` 适配器会报错，不能拿旧帧的异步模型结果决定当前帧准入。观察模式仍兼容原有外部适配器。

核心实现：`swarm_sim/rff_policy.py` 是纯观测准入规则；`runtime.py` 挂接接收和报告；`rff_evaluation.py` 只在离线评估用独立真值；`events.py` 与 `dataset/schema.json` 定义可见字段。新增配置、状态和决策字段采用增量扩展，兼容既有数据契约及默认配置的历史语义校验值。

## 7. 本次验证结果

2026-10-26，干净副本全量测试为 **704 passed**，耗时 164.05 秒，附一条第三方 Starlette 测试客户端弃用提示。复制时已逐文件核对 356 个仓库及本次新增文件；测试临时输出位于副本外，不覆盖主目录个人资料。

专项验证包括：四类外部重发路径、先于 HMAC 的准入、正常多跳、低质量保护性拒绝、空闲恢复、报告断链后补传、透明业务不解密和不执行、合法内部攻击不可观测、失败解码不算防御成功、执行器失败时日志一致、短恢复时间下的进入/退出通知，以及精确发射关联和历史数据兼容。

种子 0 至 9 的正常场景各运行 10 秒，980 次接收均为 MATCH，无确认身份异常或射频丢弃；同样 10 组种子下，外部伪装、复制型 FDI、拦截替换型 FDI、重放、Flooding 共 1240 个合格可解码攻击样本被拒绝。该结果只验证当前特征仿真参数和受控用例，不代表真实设备准确率，亦不覆盖所有强干扰和指纹相近情况。

测试期间曾有两条既有毫秒级模型超时断言在一轮全量执行中波动，单独复测其两组用例 20 项通过，最终全量也全部通过；未修改相关模型实现或放宽时间断言。主目录额外的中文命名个人 Word 文档仍可能触发既有可移植打包测试的英文路径映射要求，因此全量验收采用不含这些个人文件的干净副本。
